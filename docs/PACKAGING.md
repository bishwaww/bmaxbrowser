# Packaging, signing and updates

## What you can build where
| Target | Build on | Command | Output (`dist/`) |
|---|---|---|---|
| Windows installer (NSIS) + portable `.exe` | Windows | `npm run dist:win` | `BMAX-Browser-Setup-<v>-x64.exe`, `BMAX-Browser-Portable-<v>-x64.exe` |
| macOS `.dmg` + `.zip` | macOS | `npm run dist:mac` | `BMAX-Browser-<v>-<arch>.dmg`, `.zip` |
| Linux AppImage + `.deb` | Linux | `npm run dist:linux` | `BMAX-Browser-<v>-<arch>.AppImage`, `.deb` |
| Unpacked app (quick check) | any | `npm run dist:dir` | `dist/win-unpacked` (or the platform's equivalent) |

macOS and Linux packages cannot be built from Windows; the GitHub Actions workflow (`.github/workflows/release.yml`) builds all three on their
own operating systems. Only the **Windows x64** package has been built and run in development; the macOS and Linux targets are configured
but unverified.

## Before building: the bundled binaries
Tor, yt-dlp and FFmpeg are not in git (`resources/bin/*/` is ignored). Put them in `resources/bin/<tool>/<platform>-<arch>/` as described in
`docs/BINARIES.md`, then check them against the pinned hashes:

```bash
npm run verify-binaries          # reports ok / missing / MISMATCH
node scripts/verify-binaries.mjs --strict   # also fails when something is missing
```

Packages are built with whatever is present: a missing tool simply makes that feature say "not installed". Hashes are pinned only for the
Windows x64 files in `resources/bin/CHECKSUMS.md`; add the macOS/Linux builds and their hashes there when you fetch them. The installed size is
dominated by FFmpeg (see `docs/THIRD_PARTY.md` before shipping the GPL build).

## Icons
`resources/icons/` holds `icon.png`, `icon.ico`, `icon.icns` and `16…512` PNGs. They are generated by `npm run icons` (Electron renders the SVG in
`scripts/make-icons.cjs`), so replacing the artwork means editing that SVG and re-running the command.

## Code signing (placeholders, builds are unsigned by default)
Unsigned builds work but trigger SmartScreen (Windows) and Gatekeeper (macOS) warnings.
- **Windows:** set `CSC_LINK` (path or base64 of your `.pfx`) and `CSC_KEY_PASSWORD` before `npm run dist:win`. Uncomment `signtoolOptions.publisherName`
  in `electron-builder.yml` so updates are only accepted from your certificate.
- **macOS:** set `CSC_LINK` / `CSC_KEY_PASSWORD` (Developer ID Application certificate) and `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID`;
  in `electron-builder.yml` replace `identity: null` and set `notarize: true`.
- **Linux:** AppImages are not signed by default.
Never commit certificates or passwords; use CI secrets.

## Updates (electron-updater + GitHub Releases)
- Configured in `electron-builder.yml` (`publish:` → `bishwaww/bmaxbrowser`). The release workflow uploads the installer, its `.blockmap` and
  `latest.yml` to a GitHub release; the installed app finds them there.
- **The repository (or at least its releases) must be public.** Installed copies check without an account or token, so a private repository
  answers "not found" and Settings → About says that no published version was found.
- The app checks about 20 seconds after start and then once a day (switchable in Settings → General). When a newer version exists an **Update**
  button appears in the toolbar: one click downloads it, a second click ("Restart to update") installs it. The same is available in Settings →
  About and through Menu → Check for updates. Nothing is downloaded without that click. The request goes through the proxy setting, never Tor.
- What can update itself: the NSIS installer, the macOS `.zip`/`.dmg` install and the AppImage. The portable `.exe`, the `.deb` and development
  builds cannot (Settings → About says so).
- Updates are verified by electron-updater (file hash from `latest.yml`, and the publisher name on signed Windows builds). Unsigned builds have
  no publisher check, which is one more reason to sign releases.
- Not verified yet: a real update from one published release to the next. The update state machine and the
  toolbar button are covered by tests with a stand-in updater.

## Releasing (automatic)
Every `git push` to `main` runs `.github/workflows/release.yml` on a Windows runner:
1. picks the version: MAJOR.MINOR from `package.json` plus the next free patch number (`scripts/next-version.mjs`), so each push is a new,
   higher version;
2. runs typecheck and unit tests;
3. downloads Tor, yt-dlp and ffmpeg from their official sources and refuses anything whose SHA-256 is not pinned in
   `resources/bin/CHECKSUMS.md` (`scripts/fetch-binaries.mjs`);
4. builds the NSIS installer + portable `.exe` (`electron-builder --publish never`) and publishes them with `latest.yml` and the `.blockmap`
   through `gh release create` (electron-builder's own uploader split one version over two draft releases, so it is not used). Before that it
   deletes version-tagged releases that have no `latest.yml` (leftovers of failed runs).

Pushes that only change `docs/`, `*.md` or `tests/` do not release; `[skip ci]` in a commit message skips one on purpose. To start a new series
(for example 0.7.x) change `version` in `package.json`. The workflow can also be started by hand (Actions → Release → Run workflow).
A build takes roughly 15–25 minutes; on a private repository that uses the account's Actions minutes (Windows runners count double).

macOS and Linux packages are not built by the workflow (no pinned binaries for them yet): run `npm run dist:mac` / `npm run dist:linux` on those
systems. `npm run release` still publishes from a local machine when `GH_TOKEN` is set.

## Default browser / protocol handlers
Packages do not register BMAX as the default browser. `http(s)` links passed on the command line open in BMAX, and BMAX can optionally register as the
`magnet:` handler (Settings → Torrents).
